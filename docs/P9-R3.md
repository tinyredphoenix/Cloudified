## Implemented and checked

- Primary OpenID identity plus one same-token tokeninfo fallback for HTTP 400/401/403,
  with closed per-endpoint started/failed/succeeded traces. No fallback after network
  errors, timeouts or rate limits. Stable sub and positive expiry are required.
  Token never appears in a URL or diagnostic payload. Cached successful proof is
  tied to the exact in-memory token/expiry; renewal re-verifies identity before RPC
  or file upload, and a changed subject fails closed. Read-access no longer forces
  immediate fresh-token replacement. No email-only fingerprint or imported-token
  workflow. The Android authentication URL/body and dummy read-access hash lookup
  match pinned upstream; their different exchange/refresh hosts are not a local
  divergence. Account acceptance on iPhone remains unverified.
- Unknown Telegram 400 now gets authentication classification by the pending native
  method and caller context. Correlated failure trace remains; duplicate generic
  session/auth-method failure emissions are removed. Code/email inputs clear only
  after a successful step. Password still clears immediately; all inputs clear on
  dismissal. Numeric 406 errors remain failures without processing their message.
- Google local input inventory proves no live adapter worker/background transport
  before releasing old foreground holds, independent of credential login. Uncertain
  checkpoints remain uncertain; no recovery-complete flag or remote absence is
  fabricated. Telegram live reader inventory and global cleanup fences stay intact.
- Schema v4 recalculates the diagnostic byte counter transactionally. All event
  history now rotates, in bounded 200-row pages, using the 10 MiB/seven-day policy.
  Pruning happens inside event writes without a second progress transaction.
  Receipts, attempts, jobs/current failures, checkpoints and provider mappings are
  untouched. Legacy oversized history drains incrementally; SQLite allocated file
  size is not guaranteed to shrink (freed pages are reusable). Older app versions
  intentionally refuse the newer schema; no database reset/downgrade is performed.
- Narrow .backup.* plist and permitted/signed-bundle prefix selection follow the
  pinned reference's SideStore fallback approach. Concrete handlers register once
  per process and are reused, with at most four candidates. System submission codes
  survive into safe fallback diagnostics; unavailable grants keep foreground work.
  Continued progress uses confirmed counts plus real bytes weighted across all
  components/parts, never timer units. Fully confirmed jobs aren't counted twice;
  system progress stays below completion while assets remain. Retry/coverage changes
  may decrease real progress. No system execution guarantee or fake keepalive.
- Expiration work has an owned join task. Resume, new backup/permission work and
  account changes are fenced until it completes; shutdown joins it. This prevents
  a new continuation/run racing the old expiration cleanup.
